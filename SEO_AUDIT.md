# Technical and on-page SEO audit

Audit date: 2026-09-09

## Scope and architecture

- **Framework/build:** Next.js 16.2 App Router, React 19, TypeScript, and the Next.js production build.
- **Rendering:** hybrid. Static server-rendered pages are used by default; `/projects` and project details use ISR (`revalidate = 3600`) and server-side ImageKit lookups. Interactive presentation is hydrated through client components.
- **Routes:** `/`, `/about`, `/contact`, `/projects`, `/projects/[name]`, `/services`, and the deliberately unpublished `/experience`. `/api/contact` is not public content. Project slugs come from `src/data/projects.data.ts`.
- **Deployment:** Vercel is indicated by the Analytics/Speed Insights integrations and project URLs. The configured canonical production origin is `https://sumitvpatel.dev`.
- **Existing SEO:** App Router metadata exports, shared Open Graph/Twitter builders, a route registry, generated `robots.txt`, generated `sitemap.xml`, a web manifest, canonical metadata, and a canonical HTTP `Link` header for the resume PDF.
- **Search integrations:** Vercel Analytics and Speed Insights are present. No Google/Bing verification token or HTML verification file is stored in the repository. The reported Search Console/Webmaster Tools connection may therefore use DNS or deployment configuration, neither of which is available in this checkout; no verification mechanism was removed or invented.

## Findings and fixes

No repository evidence of a **Critical** crawl/index block on the homepage was found: the root route has no `noindex`, robots allows it, it is server rendered, and it is included in the sitemap. The findings below should improve technical consistency, relevance, and presentation, but cannot guarantee ranking.

| Severity | Category | Issue and evidence | SEO impact | Fix implemented |
|---|---|---|---|---|
| Medium | Responsive routing tradeoff | `/about` intentionally redirects mobile visitors to `/`, because the mobile homepage is the mobile equivalent of the dedicated desktop About experience. (`src/proxy.ts`.) The destination is crawlable and canonical, but `/about` remains device-dependent. | Smartphone crawlers will generally consolidate the redirected mobile URL with the homepage rather than index the desktop-only About experience separately. This does not block discovery or indexing of the homepage. | Preserved the established mobile/desktop product behavior after review. No crawler-only bypass was added because serving bots different routing would be unreliable and could be interpreted as cloaking. |
| High | Canonicalization / presentation | `SITE_URL` ended in `/`, while `canonicalUrl()` appended paths beginning with `/`. All non-root Open Graph `url` values therefore contained `//` after the host. (`src/lib/seo/index.ts`, previous implementation.) | Produces inconsistent absolute social URL signals and can fragment URL handling by consumers. Page canonical tags themselves used metadata-relative paths and were not shown to be broken. | Store a normalized origin without a trailing slash and make `canonicalUrl()` emit exactly one separator, including a canonical `/` for the homepage. Sitemap and robots now use the same origin constant. |
| Medium | Indexability / reliability | `/experience` was designated non-indexable and omitted from navigation/sitemap, but its metadata had no `noindex`; its client component called `notFound()` only after client execution. (`src/lib/seo/registry.ts`, `src/app/experience/page.tsx`, and `src/app/experience/ExperiencePageClient.tsx`.) | A crawler or non-JavaScript client could encounter an ambiguous/soft-not-found response instead of a deterministic unpublished route. This did not block indexing of the homepage. | Return `notFound()` in the server route and add explicit `index: false, follow: true` metadata. |
| Low | Heading semantics | The desktop hero intentionally uses two `<h1>` elements for the animated split-name treatment, while the mobile identity uses an `<h2>`. (`src/app/home/hero/HeroSection.tsx` and `src/components/mobile/home/MobileHero.tsx`.) | Multiple H1 elements are valid HTML and do not block indexing. The adjacent headings, metadata, visible role copy, and Person structured data still establish identity; changing these animation targets would create avoidable UI risk. | Preserved both H1 animation targets and their ref types. Did not add a third visually hidden H1 or alter the working split-name interaction. |
| Medium | Entity understanding | Metadata identified the owner, but there was no JSON-LD in the repository. The visible homepage and social-link data support a person/profile relationship. | Structured data is an entity-understanding enhancement, not a crawling requirement and not evidence of why the site currently fails to rank. | Add one JSON-LD `@graph` containing `WebSite`, `ProfilePage`, and `Person`, using only visible identity/role claims and existing GitHub, LinkedIn, and X profiles. Stable `@id` references prevent duplicate/conflicting entities. `<` is escaped before script injection. |
| Low | Sitemap quality | Every sitemap entry used `new Date()` as `lastModified`, so every build/request implied that all content had meaningfully changed; arbitrary `priority` values were also emitted. (`src/app/sitemap.ts` and `src/lib/seo/registry.ts`, previous implementation.) | Inaccurate freshness is a poor crawl hint. Sitemap priority is not needed here and is unlikely to explain ranking. | Remove fabricated `lastModified` and subjective priorities; preserve canonical URLs and supported change frequencies. |
| Low | Discovery / build coverage | Dynamic project slugs were only enumerated indirectly through the sitemap and runtime route data; the dynamic route had no `generateStaticParams`. (`src/app/projects/[name]/page.tsx`.) | The sitemap already enabled discovery, so this was not an index block. Explicit enumeration improves deterministic build-time route coverage and makes generated HTML inspection possible for every known project. | Generate static params directly from the existing project data source, without creating aliases or changing URLs. |
| Low | Robots clarity | Robots used a second origin constant solely for the sitemap and did not emit a host preference. (`src/app/robots.ts` and `src/lib/seo/index.ts`, previous implementation.) | Not a crawl block; it created avoidable domain configuration drift. | Use the single canonical origin for sitemap and host output. `/api/` remains disallowed and all public assets/routes remain allowed. |

## Audited areas with no blocking issue found

- **Metadata:** Every intended indexable HTML route has a unique title, description, canonical, Open Graph metadata, and Twitter card metadata. Root layout supplies `metadataBase`, icons, locale/site name, viewport/theme color, and `<html lang="en">`. Next.js supplies document encoding in server output.
- **Robots and sitemap:** `/` is allowed; only `/api/` is disallowed. Intended static routes, the resume, and all five project detail URLs are sourced from one registry/data source. `/experience` and the cross-canonical responsive `/services` route are intentionally omitted.
- **Internal links:** Main/footer/mobile navigation exposes the canonical home, projects, about, and contact destinations. Project list cards link to lowercase canonical detail slugs. The dynamic route redirects mixed-case aliases to lowercase and unknown slugs return 404.
- **Content:** The homepage naturally states the owner, AI/full-stack role, work, project links, availability, and contact paths. About and project data contain substantive context. No keyword stuffing or placeholder identity copy was added.
- **Images:** Audited content images use `next/image`, useful project/profile alt text, explicit responsive sizing/fill containers, and ImageKit transformations. The empty alt on the duplicate featured-project transition image is appropriate because that layer is decorative. No evidence justified renaming image assets.
- **Performance:** Fonts use `next/font`; ImageKit/Next Image are used; expensive visual modules already have deferred variants. Client animation is extensive, but the meaningful React output is server rendered and no measured bundle/Lighthouse evidence justified an architectural rewrite.
- **Canonical/redirect configuration:** Source inspection confirms consistent lowercase project URLs and HTTPS absolute metadata. The intentional mobile `/about` → `/` redirect is retained as part of the responsive product architecture; its indexing tradeoff is documented above. HTTP-to-HTTPS and www-to-apex behavior is deployment/DNS state and is not configured in this repository.
- **Index directives:** Repository search found no accidental `noindex`, `nofollow`, `X-Robots-Tag`, authentication gate, or staging/preview canonical URL affecting intended indexable pages.

## Validation plan and limitations

The implementation is validated with lint, TypeScript checking, local server-output inspection, and direct checks of generated robots/sitemap/JSON-LD. A production build was attempted but the environment could not download Inter from Google Fonts. The live production domain also could not be probed because the network proxy returned HTTP 403 for the apex, www, robots, and sitemap URLs. Therefore this audit does **not** claim to validate the production build in this environment, DNS, production redirects, deployed verification ownership, Search Console coverage, external backlinks, real-world rankings, or Lighthouse/PageSpeed scores.
